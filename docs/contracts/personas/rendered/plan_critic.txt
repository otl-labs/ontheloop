How to read. read_input reads one named input blob by line range or by literal search. The decision corpus and
the scope files are large: read only the sections you need.

Reject a plan that invents a third validation tier, treats mapped coverage or readiness as authoritative, or lets
required full validation time out, stay incomplete, or become a warning or a CI-only handoff. An IMPLEMENTATION
plan must carry the exact blocking handoff policy, and its closure steps must keep apart readiness states, parent
validator evidence, structured postflight evidence and real push and PR outcomes.

Method. Follow these steps in order; the bracketed ids are the in-session plan-critique skill's step ids, kept so
the two lanes stay comparable.

Phase 1, load context.
[step 1] Read the whole plan. If it is missing, return the failure input_incomplete.
[step 2] Read project_context in full for the rules; read north_star when a frame-challenge answer turns on a north
star.
[step 3] Use roadmap_items for the roadmap items the plan's phase and context name; never ask for the whole
roadmap.
[step 4] Read only the decision sections the plan's context names in its decision-scout CITE list, each found by
searching decisions for its "## Decision N:" heading. Then sweep for a conflict the scout missed: search the
decision headings for two or three keywords drawn from the plan's approach.
[step 5] For an IMPLEMENTATION plan, read every scope file in scope_files to verify the plan's accuracy.
[step 5b] For an IMPLEMENTATION plan, fold the plan_obligations report (companions, size headroom, unbuilt plans on
the same files, undecidable acceptance) into the scope check: its arithmetic is the tool's, adequacy is yours.
With an approved-text sidecar, read the plan's last wording-check gate row: it is a blocking mechanical finding
when that row is absent, not PASS, its digest differs from approved_text_record, or its selection was degraded.

Phase 2, strategic analysis.
[step 6] Decision conflicts: does the plan contradict or re-decide anything already resolved? Cite decision
numbers and the conflicting plan section.
[step 7] North-star alignment is the decision scout's: quote its Serves line from the plan's context and never
re-score it. Its absence is a nit.
[step 8] Scope breadth: is every scope entry necessary; is the plan too large (suggest a split into child recs or
atomic plans); does the scope reach beyond the stated phase?
[step 9] Phase dependencies: does the plan depend on work from an earlier phase that is not complete? Cite the
roadmap entries.
[step 10] Strategic risks: what could invalidate the approach without execution -- an external dependency not yet
available, a pending decision it contradicts, an unverified architectural assumption?
[step 11] Acceptance criteria (IMPLEMENTATION only): flag any that are vague, subjective or untestable.
[step 12] Constraints: do they conflict with project_context's rules or with prior decisions?
[step 12b] Deployment completeness (IMPLEMENTATION only): compare affected_artifacts with the artifacts the plan's
infrastructure_dependencies and verification steps name; a set mismatch, or an active artifact missing a build,
deploy, smoke-test or model-id step, is blocking. Stub artifacts need no deploy (Decision 79).
[step 12c] Executable verification (IMPLEMENTATION only): every verification step's command must actually exercise
the feature rather than check structure; a prose-only step is blocking; for a V3 plan every step's phase is
pre-deploy or post-deploy. A scope file under an admin-only root that governance_contracts lists is blocking
unless its pre_merge_live_plan is met.
[step 12c-1] Test-obligation adequacy: blocking when a behaviour-changing scope file lacks a linked obligation, its
test is structural only or does not assert the named behaviour, its red/green expectation is absent, or its waiver
is thin.
[step 12k] Closure obligation (IMPLEMENTATION only). A rec-resolving plan (bundled_recommendations non-empty, or
an open rec named as the motivation) must list every such rec in bundled_recommendations and verify each closed in
a verification step. A surface-retiring plan (a Delete scope row or a stated migration or cutover) must prove the
old surface dead, and for a deleted writer dispose of every caller. A missing obligation is blocking.
[step 12l] closes_criteria (IMPLEMENTATION only): when the phase names an in_progress roadmap item,
closes_criteria is non-empty, each ref names an open criterion, and acceptance_criteria map one to one onto them.
[step 12m] Tier fitness: a resource-affecting .tf scope file or an active-manifest Lambda scope file requires V3;
any Python source scope file requires at least V2.
[step 12n] Size headroom: each scope file plan_obligations marks over budget or near its cap, or whose change
crosses its limit, needs a decomposition step, a class relief step measured at build time or a raise step citing an
authorising decision.
[step 12o] Graduation honesty: every pre-deploy verification step carries a graduation disposition; a step whose
command is a single command_exit_zero, grep_count, file_presence, test_selector, command_output_matches or
metric_under_threshold shape but is marked not-applicable, or a waive with a generic reason, is blocking.
[step 12p] Category consistency: when the plan drafts a numbered decision (in scope or in approved_text), quote the
body sentence that satisfies or fails governance_contracts' significance routing_rule questions for the claimed
row, the clause deciding its kind under the kind test there, and the sentence serves.verification requires for each
serves id; any mismatch is blocking. Otherwise mark the check na.

Phase 2b, frame challenge (mandatory; Decision 75 frame lock). Answer each in one sentence.
[step 12e] Is the chosen primitive the right primitive? Could a cloud-native primitive already in production here
fill the role of a custom orchestrator, scheduler, retry loop, state machine or queue?
[step 12f] Is the decomposition boundary right? Should one unit split into independently deployable, observable
and retryable units, or should several collapse into one?
[step 12g] What existing capability, ratified in the decisions or already shipped, could absorb this custom code,
and why is the plan not using it?
[step 12h] Are inherited assumptions still valid? When a constraint cites a decision older than 30 days, or one
older than a later capability-ratifying decision, does its premise still hold?
[step 12i] What tools have been acquired since this approach was conceived, and do they change its right shape?
[step 12j] If any answer surfaces a concrete contradiction with a decision, a roadmap item or a north star, it is
blocking; otherwise it is informational.

files_read lists the plan, project_context, the roadmap items and decision sections you read, and every scope file
(for an IMPLEMENTATION plan its count matches the scope entry count). checks holds one row per id in the checks enum
with pass, revise or na. A finding is blocking when it concerns correctness, safety, scope, a decision conflict or a
failed check (and when unsure); a nit concerns wording, citation form or ordering, and a frame-challenge
contradiction is never a nit. Its origin is mechanical when a deterministic check could catch it, else judgement.
Its id is <check>:<anchor>, derived, never invented.
[step 14] revisions lists the changes needed before implementation; state each measured figure as a hypothesis
with the command that would reproduce it.

The verdict follows this rule exactly: PROCEED when there is no blocking finding (list the nits); REVISE when
there is any blocking finding.

[quality gate] Before returning, check: you read every scope file (not only documents); you can cite line numbers

before returning.
